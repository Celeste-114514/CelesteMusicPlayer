## 播放栏封面"很糊"（用户 10-19 报，且怀疑没走缓存）
- **实证结论：一直在走缓存**，用户直觉不成立。证据：日志 `[播放栏封面] 缓存=命中 像素=160x160`
  （本轮新加的自检行，在 logs/app/ 当日日志里搜「播放栏封面」）。
- 真因是**档位太小 + JPEG 默认质量**：
  - 旧 Thumb 档 = 96（磁盘 v1 缓存实测 Thumb.jpg 全是 96×96），播放栏显示 58px，
    200% 缩放就是 116 物理像素 → 96 被放大，而歌曲面板走的是 Album 320 档（所以清楚）；
  - 缩略图 JPEG 用编码器默认质量，小图块效应明显。
- 修法：`CoverArtService` Thumb **96 → 160**，JPEG 编码质量设 **0.92**（`BitmapPropertySet` + `BitmapTypedValue`），
  CacheVersion **v1 → v2**（旧 v1 目录自然失效，不用迁移）。缓存目录实测已生成 v2：Thumb 160×160 / Large 768×768。
- ⚠ 副作用要告知用户：Large 768 档质量 0.92 后单张约 258KB，缓存会明显变大（设置里可一键清除）。
- 播放页大图改走 Large 768 档（10-19 已有改动），本轮一并生效。


## 零散播放窗口：拖动「还是拖不动」的真正根因（用户 10-19 二次反馈）
自动化实证（`_drag_probe_scattered.py`：模拟真实鼠标按下-移动-松开，读窗口坐标差；
对照实验 `_drag_probe_control.py` 拖记事本 dx=120 证明手法有效）后定位到**三个叠加的坑**：

1. **`IsLeftButtonPressed` 恒为 false** —— RootGrid 开了 `AllowDrop`（要接拖放进来的文件），
   鼠标按下走的是拖放输入路径，`e.GetCurrentPoint().Properties.IsLeftButtonPressed` 读不到，
   那句"必须是鼠标左键按下"的守卫每次都直接 return。**已删掉这句判断**。
2. **`IsControlElement` 无限往上追溯把顶栏判成了控件**（日志实证：`判为控件=True`）——
   从 DragBar 一路追到窗口内容根里某个滚动容器就命中了。**改成最多查 3 层**。
3. **SetCapture 到顶层窗口 + 子类化收 WM_MOUSEMOVE 无效**（按下能进、捕获也调了，窗口不动）。

最终定案 = **轮询定时器**（`StartPollingDrag`）：按下那一下进来后，16ms 一帧自己
`GetCursorPos` + `AppWindow.Move`，用 `GetAsyncKeyState(VK_LBUTTON)` 判松手。
不依赖任何指针事件路由 / 捕获。实测顶栏把手 + 中部空白都 DRAG=OK（dx=120 dy=60）。

⚠ 排查方法上的两个教训（值得复用）：
- **别强杀进程收场**：`p.kill()` 会把日志缓冲里没落盘的行带走，我因此误判过一次
  "事件根本没到"。要发 WM_CLOSE 让它自己正常退出再读日志。
- **探测前先确认坐标上是谁在接鼠标**（`WindowFromPoint` + `GetAncestor`）：
  本机常驻全屏的街霸6，不换位置/不置顶会测出假 FAIL。
