## 15:10 更正上一条：TTA 时长算错了一半（已修）

上一条写的「TTA 时长全 = 0.25 秒（文件头真值）」**是错的** —— 那是拿同一个错误公式自证。
ffmpeg 解码出来是 **0.50 秒**。

- 真因：TTA 头 offset 14 是**总采样数**，不是压缩数据字节数。旧式
  `字节数×8/(采样率×声道×位深)` 会把 16bit 单声道的时长**除以 2**（立体声 /2、24bit /3）。
  正确算法只有一句：`秒 = 总采样数 ÷ 采样率`。
- 验证方法（别再自证）：用打包的 ffmpeg 现造 4 个已知时长的样本反推头部含义 ——
  1s 单声道 44.1k → 字段=44100、1s **立体声** 44.1k → 仍 44100、1s **24bit** 48k → 48000。
  三种都等于「采样率 × 秒」，跟声道数/位深无关。
- 新增 `tools/_w13_tta_check.py`：探针出数后，拿 ffmpeg 解码时长当基准逐条比，
  不通过就非零退出。⚠ 只跑 W13TtaLibraryProbe 不算验证 —— 它和被测代码是同一个公式。

## 顺手把 10 种格式的时长都跟 ffmpeg 对了一遍（结论：只有 TTA 是我们的锅）

`tools/TagLibDurationProbe`（新，独立小项目，`dotnet run --project` 直接跑）能直接问
TagLib「这个文件多长」，用来区分「TagLib 读错」还是「我们换算错」。

| 格式 | 曲库 vs ffmpeg | 定性 |
|---|---|---|
| flac / wav / m4a / ogg / opus / wma / ape | 一致 | 没问题（m4a 3719 首、flac 303 首是用户主力格式） |
