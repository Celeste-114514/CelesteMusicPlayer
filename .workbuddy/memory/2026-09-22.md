## MusicPlayer2 源码调研（用户提供 C:\Users\admin\Downloads\Download\MusicPlayer2-master）

C++/MFC + BASS。结论（带 file:line，由 Explore 子代理核实）：
- **三个播放内核**：BASS（默认）/ MCI / FfmpegCore（外挂 DLL）。
  **独占模式只存在于外挂的 ffmpeg_core.dll 里，本仓库没有实现**（FfmpegCore.cpp:721-731 只转发设置）。
  BASS 内核一次 `BASS_Init(…, 44100, BASS_DEVICE_CPSPEAKERS /*unused*/, …)`（BassCore.cpp:69-79），
  **全仓库零次 `BASS_SetConfig`** —— 缓冲/更新周期全是默认值，没有任何设备周期协商。
- **零 STREAMPROC、零自制环形缓冲**（BassCore.cpp:312 一行 `BASS_StreamCreateFile` 完事），
  播放路径上应用一行 PCM 搬运代码都没有，全外包给 BASS 内部解码线程。
  → 回调里不可能阻塞读盘/等锁，因为根本没有回调。
- **零磁盘 PCM 缓存**，只有 %TEMP% 下一个反复覆盖的封面临时图 + 元数据 DB song_data.dat。
  → "缓存快满了要一次性删几百 MB"这个问题在它那里根本不存在。
- 无 gapless、无交叉淡化、无下一曲预解码。EQ/混响即使关掉也不 bypass（反面例子）。
- 防爆音手法只有一个：`std::timed_mutex` + `try_lock_for`，UI 侧永不死等
  （ProgressBar.cpp:26 用 1s；位置轮询用 10ms，拿不到就跳过这一帧）。
- 进度条**只在鼠标抬起时 seek**，天然免节流。歌词每 ~100ms 查真实位置，不维护独立时钟。

**对本项目最有价值的一条**：它没有任何"大文件优化"（无内存映射、无分块读），
大 FLAC 依然稳 → 佐证"MP3 也卡"不是 I/O/文件大小问题，而是周期性的主线程工作 + GC。

## 实机日志回读：修正两个误判 + 抓到 MP3 32bit 真 bug（提交 b35b87b，未 push）

用户反馈"卡顿依然存在"，回读 01:07-01:09 的实机日志，本轮推翻了上一轮的两个结论：

**推翻 1：`读源耗时尖峰=15-16ms` 是假的。**
诊断用 `Environment.TickCount64` 计时，精度只有 ~15.6ms（Windows 默认时钟粒度），
任何跨 tick 的读取都被量化成 15/16ms。日志里每次读数都恰好落这个值 —— 时钟粒度假象，不是磁盘慢。
→ 已全面改用 Stopwatch。**教训：测毫秒级耗时绝不能用 TickCount64 / DateTime.Now。**

**推翻 2：`underrun` 每 100ms 一次不是真欠载。**
独占 + 事件驱动下周期恒等于缓冲，`GetCurrentPadding` 在每个周期边界必然归零一次。
旧日志计数严格每 2.1s +21（每 100ms 一次），规律得不像故障；
而"源没喂满"这种**真**欠载在整份日志里 **0 次**。
→ 判据改为缓冲水位（最低/平均/空缓冲占比），真欠载单独计数。
**教训：独占模式下 pad==0 不能当欠载指标，它基本等于设备事件计数。**

**抓到的真 bug：有损源被误判成 32bit（FfmpegDecoderBackend.ParseStreamFormat）**
MP3/AAC/Opus 解码器输出是 `fltp`（浮点平面），旧代码当成"源位深 32bit" → 转码选 `pcm_s32le`，
WAV 缓存体积翻倍（5 分钟 MP3：53MB→106MB），越过 64MB 阈值掉进"8MB 流式读盘"，
播放时每 12ms 打一次磁盘。**这就是"MP3 明明很小也卡"的直接原因**。
实测：日志里 4 个 MP3 全部被判成 44100hz/32bit/2ch。
修：无括号位深声明 + 浮点输出 → 16bit。FLAC/ALAC 24bit 带 "(24 bit)" 括号，不受影响。

**64MB 阈值太低**：实测缓存 33 个 WAV 里 13 个（39%）超 64MB → 全部流式读盘。
24bit/44.1k ≈15.9MB/分钟、24bit/96k ≈34.6MB/分钟，正常长度的歌必然超。
提到 192MB + 安全阀（可用内存 <1.5GB 退回流式，防重演 2~3GB 内存暴涨）+ 走哪条分支打日志。

**新诊断能直接归因**（每 10 秒一行 `[渲染统计]`）：
水位健康 + 间隔尖峰多 → 系统侧（GC/DPC/驱动，应用救不了多少，建议 LatencyMon）；
水位贴 0 + 读源慢 → 磁盘侧（需 feeder 队列 = 阶段三）。
新增 `[读源] 整读内存/流式读盘 XX MB` 日志，可验证 MP3 修复是否生效。

**下一步**：等用户实机复测。若归因指向系统侧，重点怀疑 Clash TUN / 火绒内核驱动 / 雷神加速器
造成的 DPC 延迟（FiiO KA13 是 USB DAC，独占模式对 DPC 极敏感）。
注意：位深判定改了 → 转码参数与缓存 key 都变，MP3 首次播放会重转码一次。

## 用户纠正：规格显示不许按类别猜（提交 2ef9eee）

用户看了我的思考过程后明确纠正：**"音频的信息显示方面肯定显示真实的采样率/位深/比特率，
而不是像你说的那样有损音频一律 16bit，要牢记我们程序是一个音频播放器。"**

**我错在哪**：上一提交为了修 MP3 虚标 32bit，加了 `IsLossyCodec → 一律 16bit` 的兜底。
这是**用类别去猜，等于把真实信息抹掉**：
- WMA Lossless、DTS-HD、E-AC3 这类容器里照样能装 24bit 有效精度
- 32bit float 的 WAV/FLAC 真实位深就是 32，钳成 16bit 是虚标+降级

**改成 ParseBitDepth（AudioInfoFormatter.cs:654），严格按可信度分层，拿不到就返回 0 不显示**：
1. 括号声明 `(24 bit)` —— ffmpeg 对整数打包格式的**权威有效位深**
   （24bit FLAC/ALAC 报 `s32 (24 bit)`，32 只是容器位宽）
2. 整数采样格式 s16/s24/s32/u8 及平面变体 → 位深一一对应
3. 浮点 fltp/flt/dbl —— **解码器内部格式**，真实位深看 codec：
   pcm_f32le→32 / pcm_f64le→64 / flac(float)→32 / dsd_*→1 /
   mp3,aac,vorbis,opus,mpc,wma,atrac3,cook,speex→16（ISO 规范下解码输出就是 16bit PCM，
   这是真实值不是猜测）/ 其余未知→0
4. 都不匹配 → 0（调用方 `bits > 0 ? bits+"bit" : ""` 会省略该字段）

**顺带抓到更严重的**：播放链路（FfmpegDecoderBackend fltp 分支）把 **32bit float 源
降级成 16bit 转码**——那是真丢精度，播放器不能接受。已改按 pcm_f32/pcm_f64/float-FLAC
分别给 32/64/32。有损仍 16bit（既真实，也避免 WAV 缓存翻倍越过阈值掉进流式读盘）。

**关键认知：两个场景目标不同，不能互相套用**
- 播放链路（选转码输出格式）：允许为性能取舍（体积/阈值）
- 信息显示：必须报告真实值，不许猜
- 位深**不持久化**（`tracks` 表无该字段，只存标签），显示时实时探测 + 进程内 InfoCache
  → **改完重启即生效，不用清曲库索引**。我上一轮担心的"索引里存着旧 32bit"是误判，
  日志"索引命中 3610 首，实际解析 0 首"说的是**标签**，不是音频规格。

## 卡顿归因转向 GC（提交 adbabe5）：101ms 尖峰实锤 + ECHO 同机不卡推翻系统层判断

**新日志的实锤读数**：`[渲染诊断] 补货间隔尖峰=101.1ms` —— **超过 100ms 缓冲**。
设备在这 101ms 里必然啃光存货并饿着 = 可闻断音的直接解释。
（此前 34~86ms 还在缓冲容量内，只能算"可疑"。）
同轮三项排除磁盘：读源最大 0.19~3.39ms、真欠载 0 次、平均水位 85%。

**用户实测推翻我上一轮的归因**："clash 等进程是无关的，因为我用 echo 播放歌曲就没有问题"。
同样的机器/驱动/USB DAC，ECHO 稳、Celeste 卡 → 问题在代码层面差异，不是环境 DPC。

**新归因：.NET GC 的 STW**
- ECHO 音频核心是 **Rust，没有 GC**；Celeste 是 C#。
- 一首歌整读 37MB + 预载 33MB 进大对象堆 → gen2/LOH 回收是 **STW**，
  暂停**所有**托管线程，渲染线程再高优先级、MMCSS "Pro Audio" 也躲不掉
  （不是调度问题，是运行时直接冻线程）。
- 三条现象全吻合：**起播时尤为明显**（此时分配最多）、**跟文件大小无关**、**ECHO 不卡**。

**已加诊断（复测即可定性）**：
- 每次尖峰打印 `GC: gen0+N gen1+N gen2+N 堆=XXMB 模式=X` —— **看 gen2：涨了=GC 元凶，0=系统/驱动侧**。
- 新增"断流"计数：间隔 > 缓冲真实时长(帧数/采样率) → 必然断音的硬指标。
- 统计行同步带 GC 增量 + 堆大小 + LatencyMode。
- App 启动设 `GCSettings.LatencyMode = SustainedLowLatency`（gen2 尽量后台回收），
  日志打印 `[GC] 已设为低延迟模式 ...` 确认生效。
- 顺手修：独占 USB DAC 上 `IAudioEndpointVolume` 的 QueryInterface 恒失败(E_NOINTERFACE)，
  改首次失败后记标志不再重试（原本每次抛异常+写日志）。

**照搬 ECHO 方案的影响评估**（详见 `ECHO方案照搬的影响评估-2026-09-22.md`）：
- **最关键：如果 daemon 也用 C#，GC 一个都没解决**。ECHO 不卡一半靠独立进程，
  一半靠**它是 Rust 没有 GC**。想真正解决，daemon 必须用非托管语言。
- 用户担心的功能：无缝切歌**变简单**（不用管 WAV 格式一致）；歌词/进度条基本无感
  （位置改由音频侧定时推）；**DSP、交叉淡化、DSD 直出要重写**；**bit-perfect 需重新验证**。
- 其它：起播立刻出声、内存大降、转码缓存可废弃；但复杂度/维护成本大幅上升
  （用户不懂编程，链路全改后难自查）。
- **建议顺序**：0 缓冲调 200/300ms（改设置，立刻能试）→ 1 GC 低延迟（已做）
  → **2+3 不整读内存 + 非托管环形缓冲 + 渲染线程只 memcpy（拔掉 GC 根因）**
  → 4 取消落盘改流式（可选，主要收益是起播快，不是治卡顿）
  → 5 独立进程（高成本，且必须非托管语言才有效）。

## NAudio 3.1.0 源码调研结论（用户提供 C:\Users\admin\Downloads\Download\NAudio-3.1.0）

用户想"改底层"，并搬来 NAudio 源码。读完 `src\NAudio.Wasapi\WasapiOut.cs`（旧，已标 Obsolete）
和 `WasapiPlayer.cs`（新，builder 创建）后的结论：

**NAudio 独占模式的实现，和我们自研的 NativeWasapiExclusiveOut 几乎一模一样，没有任何我们没有的机制**：
- `Initialize(Exclusive, EventCallback, latencyRefTimes, latencyRefTimes)` —— 周期=缓冲（微软铁律，和我们一致）
- 渲染线程：`WaitHandle.WaitAny([frameEvent, stopEvent], 3 * latencyMilliseconds)` —— **等设备事件**
- 每次醒来：**独占模式直接把 padding 当 0**（不看 CurrentPadding）→ 填满整个 `bufferFrameCount`
- `FillBuffer` 从 IWaveProvider 读满整缓冲 → GetBuffer → Release(frameCount)
- WasapiPlayer 多了 MMCSS（`AvSetMmThreadCharacteristics`）+ `GetBufferLease` 零拷贝 Span 读

**与我们实现的差异（我们并不差，反而更稳）**：
- NAudio 是"踩点"：每个事件（=每整缓冲被啃光一次）才填一次整缓冲；
  我们是**主动轮询** pollMs=缓冲/8 + 只补空闲空间（读 GetCurrentPadding），水位维持 94~97%
- NAudio WasapiOut 连 MMCSS 都没有（线程普通优先级），WasapiPlayer 才有；
  我们 Highest + Pro Audio
- **IAudioClient3 低延迟只支持共享模式**，builder 对 exclusive 直接拒绝（源码注释明说）→ 对独占无效

**另一个关键点（解释"共享没问题独占有问题"）**：共享模式 Windows 音频引擎带
`AutoConvertPcm`，会把源**重采样到设备 mix format（通常 48k）**再播；独占是**原样直通**
（96k 源就是 96k 送 DAC）。所以"共享不卡"很可能不是我们代码好，而是 96k 直通链路
（USB DAC 驱动/固件）本身不稳 —— 这也能解释 DSD 也卡+底噪两条线交汇。

**结论：照搬 NAudio 独占 = 大概率白换**。真正区分问题域的实验是**共享模式播同一批 24/96 歌**
（共享会走 48k 引擎转换）：不卡 → 96k 直通链路问题，与渲染循环无关。
