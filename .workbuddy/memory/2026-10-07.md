# 2026-10-07 工作日志

## ★★★ 第三轮：1.2G 占用优化（用户实测 4G→1.2G 后要求压到 700M 以下，给后续皮肤系统留空间）
### 1.2G 的构成（第二次实测，18:35:56 启动那轮的数据，干净）
-启动 21MB → **主窗口加载完 449MB**（含视频背景 105MB）→ 播第1首 688MB → 播到第4~5 首 **1352~1406MB**
- 托管堆全程只有 100~160MB、**非托管 1.16GB**；最后一次启动（关掉视频背景）主窗口加载完只 **132MB**。
### 真凶一：GC 开着 SustainedLowLatency（App.xaml.cs）
2026-09-22 为修**独占模式** STW 卡顿加的，**却对所有输出模式都开了**。
该模式让 GC 几乎不回收 → 3609 首曲库加载完堆到 449MB，差额全是没回收的垃圾。
而实测输出全是 `mode=WasapiShared`（共享模式），系统混音器在下游兜着，**根本没有独占那个 STW 卡顿问题**。
**修法**：读`AppSettingsStore.Load().OutputMode`，只有 `WasapiExclusive` / `Asio` 才开低延迟 GC；
`WasapiShared` 用 `GCLatencyMode.Interactive`（正常回收）。日志会打两种不同文案，便于确认走了哪条。
判定依据：SettingsWindow.xaml.cs:448-449 只有三个取值 WasapiShared / WasapiExclusive / Asio。
⚠ 保留了原注释里的历史背景（独占 STW 挂起 34~101ms vs 缓冲 100ms），别删，那是决策依据。

### 真凶二：默认 GC 不主动还内存
改成 Interactive 后它是「按需回收」，不会主动还给系统。
新增 `MemProbe.CollectAfterTrackChange(bool playing)`：在 `PlayWavAsync` 里 `StopCore()` 之后调用，
`GC.Collect(1, Forced, blocking:true)` —— **只收 Gen1 不碰 Gen2**（Gen1 几毫秒，Gen2/LOH 几十上百毫秒）。
⚠ **只在不播放时收**（内部判 `playing` 直接 return）：播放中收 STW 会挂起渲染线程造成可闻断音，
这正是当初引入低延迟 GC 要规避的问题。放在切歌瞬间是因为 StopCore 已 Dispose 旧 reader、旧数据无人引用。
释放超过 8MB 才打日志，避免刷屏。

### 阈值放宽 0.9GB → 1.5GB
初版设 900MB 太保守：日志打「内存不足，安全阀退回」可实际才 1.2G，
而 1.2G 里绝大部分是没回收的垃圾 → 11 次误退流式。GC 修好后基线降了，阈值相应放宽。
第一道防线是释放修复，这道闸只是兜底。

1. **exe 被锁**：用户在跑 `bin/.../CelesteMusicPlayer.exe` → `MSB3027文件被 CelesteMusicPlayer (pid) 锁定`。
   此时**编译其实已成功**（obj 下的 dll 已更新），只是最后拷贝 exe 那步失败。
   处理：把 `obj/.../CelesteMusicPlayer.dll` 直接 `cp -f` 到 `bin/`（exe 只是apphost 启动器，不用动）。

## ★★★ 第二轮：真凶是「视频背景」，不是 PCM（第一版诊断被数据推翻）
用户装上第一版后反馈「播放后内存超 4G」。用 MemProbe 数据 + 日志交叉验证，**第一版结论（PCM 泄漏）不成立**：
- `无缝诊断` / `已释放旧reader` / `已无缝续接` 三个计数**全为 0** → 我修的那条路径一次都没走到。
- `自定义背景：视频已应用` 出现 **14 次**；非托管内存 104MB → **4373MB**（单次跳变 **+3.1GB**），
  跳变点正好在「背景视频：窗口最小化，已暂停解码」那一行。
### 根因（已修）
`MainWindow.UiTheme.cs` 的 `ApplyCustomBackgroundVideo`：
1. **每次调用都 `Source = MediaSource.CreateFromUri(...)` 重建源，旧源从不 Dispose**
   → WinRT 原生对象靠引用计数，旧的解码器与帧缓存一份份堆着。
2. `StopCustomBackgroundVideo` 里只 `Source = null`，**那只是松引用，不释放解码器**。
### 官方正确的释放序列（微软文档 play-audio-and-video-with-mediaplayer / MediaPlayerElement）
```csharp
IMediaPlaybackSource source = mediaPlayer.Source;   // 先取，置 null 后取不到
mediaPlayer.Pause();
mediaPlayerElement.Source = null;
mediaPlayerElement.SetMediaPlayer(null);   // 少了这步元素仍持有，Dispose 后不回收
if (source is MediaSource ms) ms.Dispose(); // 释放方法是 Dispose()，【没有 Close()】
```
⚠ 我一开始凭直觉写了 `ms.Close()` → CS1061「MediaSource 未包含 Close」。
**教训：WinRT 的释放方法别猜，`Close`/`Dispose`/`Release` 各类型不同，必须查官方文档。**
⚠ `IMediaPlaybackSource` 接口**不暴露** Dispose（只有 MediaSource 具体类型有），写 `else src.Dispose()` 会 CS1061。
⚠ 本机 **反射（Assembly.LoadFrom / GetType）被安全策略拦截**（"execute arbitrary .NET code"），
   查 API 只能靠 WebFetch/WebSearch 官方文档 + 编译错误反馈。
新增 `CloseBackgroundVideoSource()` 统一收口，三处调用（换源前 / StopCustomBackgroundVideo / 关窗 Dispose）都走它。
⚠ 因有 `SetMediaPlayer(null)`，换源后必须**重新 `SetMediaPlayer(_backgroundVideoPlayer)`**，否则视频不显示。
另加「同一路径 + 源仍在 → 跳过换源」的判重（新增字段 `_backgroundVideoPath`），
直接掐掉那 14 次重复调用（日志会打 `视频背景重复应用(同路径,已跳过换源)`）。

## ★ 紧急刹车：整读 PCM 的安全阀形同虚设（已修）
`HasEnoughMemoryForWholeFile()` 只看 `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes`（**系统**可用内存）。
本机 16GB → 这个阀**永远满足**，等于没有，进程涨到 4G 它还在放行。

## ★ 内存排查：播放一首歌进程涨到 1G+（本次主要产出）
### 定位到的真凶：SeamlessWaveProvider 泄漏整份 PCM（已修）
`SeamlessWaveProvider.cs` 两处把旧 reader 顶替掉时**从不 Dispose**：
- `ReadUnsafe` 硬切分支（`_current = next`）
- `FinishCrossfade`（`_current = _next`）
注释原写「旧 current 的释放交给上层」，**但上层 `_waveFile` 指向的是提升后的新 current，永远不会释放旧的那个**。
日志佐证：同一首 136.1MB 的 WAV **整读 8 次、一次流式都没走**（`流式读盘` 计数 = 0）。
根因链：`UnmanagedMemoryFileStream` 用 `Marshal.AllocHGlobal`，**GC 完全看不见**；
136MB 不构成 GC 压力 → GC 迟迟不跑终结器 → 一首接一首攒到 1G+。
**修复**：新增 `ReleaseExpiredReader()`，在换引用那一刻显式释放（此处已持 `_sync`，render 不会并发用旧 reader）。
用 `_releasedKeys`（HashSet + `RuntimeHelpers.GetHashCode`）对二次 Dispose 做幂等短路——
因为上层 `HandleOutputPlaybackStopped` 里还有 `_waveFile?.Dispose(); _waveFile = nextReader;` 会碰同一对象。
`SetCurrentUnsafe` **故意不释放**旧 current（它可能被上层同时持有，抢着释放会埋双重释放/竞态）。
**该项目的 `SetCurrent` 全项目无调用方**，切歌走别的路径。

### MemProbe（内存自检工具，`CelesteMusicPlayer/MemProbe.cs`）
进程外手段读不到托管堆细分（.NET 9 上 CLR 性能计数器对外部进程不可用），让程序自己报数：
`ManagedHeap / TotalCommittedBytes / LOH / PrivateBytes / 工作集 / 线程数`，并**自动算相对上一次的增量**（Δ托管/Δ非托管/ΔWS）。
插桩点：OnLaunched、MainWindow 已加载、PlayWavAsync 起播后、整读 PCM 后、无缝预载下一首后、
**无缝切换到下一首后**（验证泄漏修复的关键证据）、视频背景应用后、视频暂停后。
周期采样用**环境变量开关**：`CELESTE_MEMPROBE=1`（每 5 秒一行），默认关，不干扰播放。
`LogAfterGC` 走 `GCCollectionMode.Aggressive` 双次强制 GC，只用于排查，正常播放路径别开。
⚠ 坑：`.NET 9` 的 `GCGenerationInfo` **没有 `Generation` 属性**，LOH 只能按下标取 `GenerationInfo[3]`。
