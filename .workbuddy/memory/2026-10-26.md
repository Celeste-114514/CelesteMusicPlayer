## 第三轮：弹窗定位改正（用户明确要的行为）

**用户需求原话**：「除了在右侧的那个音频设置按钮没办法以外，这两个窗口都应该
以按钮的水平位置为中轴位置上左右对称」。

我上一轮把 `#transport-dialog` 用 CSS `left:50%;top:50%;translate:-50% -50%` 强行居中是**错的**，
因为 `transport-panels.js` 的 `placePanel()` 本来就在按触发按钮定位，写的是 **inline left/top**。
inline 会盖掉 CSS 的 left/top，**但盖不掉 CSS 的 translate** → 面板在被算好的位置上又偏半个身位。

正确做法：
- `placePanel()` 的 left 算法改成**按钮水平中心对齐**：`anchor.left + anchor.width/2 - width/2`
  （原来是 `anchor.right - width`，纯右对齐），再 clamp 到 `[16, innerWidth-width-16]`。
  音频设置按钮太靠右 → clamp 后贴边，无法对称，这正是用户说的"没办法"，属预期。
- CSS 只留无锚点兜底：`right:24px;bottom:134px`（播放栏 108px + body padding 14px + 12px 间隙），
  **用 right/bottom 不用 left/top/translate**，避免和 inline 打架。
- 补了 resize 时重算位置。

### 二、net9→net10 升级：在本机做过真实编译试验，结论是「可行且便宜」
- ⚠ **`global.json` 是未跟踪文件**（`git status` 显示 `?? global.json`，不在版本库里），内容 `{version:9.0.317, rollForward:"disable"}`。
  这台机器被它锁死在 SDK 9.0.317：**直接 `-p:TargetFramework=net10.0-...` 会报 NETSDK1045**，
  看着像「本机不支持 .NET 10」，其实本机 SDK 10.0.401 和运行时 10.0.8/10/12 都装着。这也是「=0 files」假象的来源之一。
- ⚠ **`-p:TargetFramework=` 不足以跑 restore**：只改 build 的话会报 NETSDK1005（assets 文件没有 net10 目标），
  因为 restore 图用的还是 csproj 里的 net9。真试验必须**临时把 csproj 的 TFM 也改掉**再 restore。
- 试验结果（临时改 global.json→10.0.401 + csproj TFM→net10.0-windows10.0.19041.0，跑完立刻还原）：
  **RESTORE exit=0 (84s)、BUILD exit=0 (68s)，0 错误 / 170 警告**。
  → 现有锁定的 WinAppSDK 1.8.2511xxxxx 全家 + CommunityToolkit DataGrid 7.1.2 在 net10 下**直接可用，无需换包**。
- ⚠ **Python 改写 csproj 会丢 BOM**：`open(...,encoding="utf-8-sig")` 读会把 BOM 吃掉，再用 `"utf-8"` 写回去就没有 BOM，
  git 会显示 ` M`（1 insertion/1 deletion）。临时改 csproj 后用 `git checkout -- <file>` 还原最稳，别手写恢复。
- 试验后回归：`_build_check.py` BUILD_OK 一次过（44s），obj 没被 net10 试验污染。

### 三、升级效益判断（给用户的口径）
- 时间压力真实：**.NET 9 STS 支持 2026-11-10 结束**（距今 15 天）；.NET 10 LTS 支持到 **2028-11-14**。
- 但本项目是**自包含发布**，运行时随包走，目标机不装 .NET 也能跑 —— 所以「必须升级」的压力低于普通框架依赖应用；
  真正的代价是：11-10 之后 net9 运行时**不再有安全补丁**，你发出去的包里就带着一个不再修的运行时。
- 收益：LTS 到 2028、JIT/GC/启动的优化；**拿不到的收益**：Native AOT（WinUI 3 不支持）、剪裁（PublishTrimmed 已关，
  且 DataGrid 反射多会误删）、语言版本 C# 14 只是语法糖。
- 风险点（真做时要验）：未按 net10 重编的本机 DLL（celeste_core / celeste_dsp_core / celeste_audio_core）是 **C ABI**，
  理论上与运行时版本无关；真正的雷是 XAML 编译器和 CsWinRT 的运行时行为，必须**实机跑一遍**再定，不能只靠编译通过。
