## 用户拍板的三个决定（2026-10-13 凌晨，已确认）

1. **联网功能只留 MusicBrainz 系**
   - 保留：MusicBrainz（元数据）+ Cover Art Archive（封面）+ Last.fm 官方 API
   - 删除：网易云 `music.163.com/api/*`、QQ `c.y.qq.com`/`u.y.qq.com`/`y.gtimg.cn`、
     酷狗 `songsearch`/`lyrics`/`mobilecdn`、iTunes（含 `music.apple.com` 网页抓取）
   - 歌词改用 **LRClib**（`lrclib.net/api`，免费无需 key，只需 User-Agent）
   - 艺术家简介改用 **Wikidata / 维基百科**（CC BY-SA，中文条目也有）

2. **排序不写回文件**（用户澄清，重要）
   - 用户原话：mp3tag 的列表排序是不动文件的，实际用法是「按某种方式排列 → 多选音频 →
     加入播放队列/播放列表」，这样就达到目的了。
   - ⚠ 设计含义：排序 = **视图层排列**，不是改写 track number。真正要改文件里的顺序
     是另一个动作（自动编号）。上次 TagSort 被删很可能就是卡在这里。

3. **标签编辑 + 标签排序 = 合并成一个「标签」板块**
   - 用 ShellPageHost 分「快速编辑 / 批量工具 / 排序编号」子页，不出两套 UI。

## 平台接入门槛核实结果（2026-10-13 查证）

| 平台 | 要不要申请 | 说明 |
|---|---|---|
| MusicBrainz `/ws/2` | 不需要 | **限速每秒 1 请求**，强制 User-Agent `应用/版本 (联系方式)`；默认 UA（python-requests 等）直接封 |
| Cover Art Archive | 不需要 | MB 姊妹项目，按 release MBID 取封面 |
| LRClib | 不需要 | 官方明示「no API key, no registration」；批量建议 200–500ms 间隔 |
| Wikidata / Wikipedia | 不需要 | CC BY-SA，SPARQL/REST 均可 |
| Discogs | **需要注册拿 token** | 注册 discogs.com → Settings → Developers → Generate token。匿名也能读（25/min），有 token 60/min，但匿名拿不到图片 URL |
| Last.fm | **需要注册拿 key** | last.fm 注册 → `last.fm/api/account/create` 填应用名 → 拿 api_key + shared_secret |
| fanart.tv | **需要注册拿 key** | 免费，VIP 档更快 |
| AcoustID | 需要申请 + **商业付费** | ⚠ 项目仓库公开，谨慎 |
| 网易云 / QQ | **有开放平台但不对普通开发者开放** | 网易云 `developer.music.163.com` 需入驻+凭证；QQ `developer.y.qq.com` 需商务合作。项目里用的老接口是逆向抓包，与开放平台无关 |

## 用户答疑记录

- **Q：Discogs 不需要 create an application 吗？**
  A：不需要。Discogs 两种认证：① Personal Access Token（个人自用，Settings→Developers→
  Generate new token，够用）；② OAuth Application（只有软件要替别的用户登录、读写其收藏/订单
  时才需要）。本项目=自用+只读 → PAT 足够，且免 OAuth 跳转与 token 存储。
- **Q：fanart.tv 的 API key 在哪？**
  A：不在个人页，是专门地址：注册登录后访问 https://fanart.tv/get-an-api-key/
  页面分 Project API Key 与 Personal API Key 两块，**两个都生成**。
  ⚠ Kodi 社区反馈：集成到应用时 Personal key 可能不正常工作，故两个都要，
  代码里优先 client_key、失败回落 api_key。
- 艺术家头像：保留 UI 与本地逻辑，仅把联网取图源换成开放平台 ✅ 用户确认理解无误

## 曲库管理 + 标签编辑现状审查（用户点名要做「上万首流畅」评估，只审不改）

用户目标：上万首大曲库流畅且不占内存；自评标签编辑不如 Kid3。要求把两块现状理清。

### SQLite 现状（用户问「有没有」——有，而且是核心设施）
- `Microsoft.Data.Sqlite` 10.0.11 已在 csproj；库文件 `%LOCALAPPDATA%\CelesteMusicPlayer\library.db`（WAL）。
- 表：`playlists`/`playlist_songs`（命名单）、`library_session`（上次会话）、
  `tracks`（曲库标签索引，file_path 主键 + mtime_utc/size 指纹校验）、`playback_history`。
- 旧 JSON 数据一次性迁移+备份（LibraryDb.EnsureMigrated），失败回退内存态。
- **定位偏差**：SQLite 现在是「启动加速缓存」，不是「曲库本体」——曲库本体仍是启动时
  全量物化进内存的 `_playlist`（ObservableCollection<PlaylistItem>）。

### 曲库加载链路（MainWindow.Library.cs）
RestoreLastLibraryAsync → LoadLibraryFilesAsync → BuildPlaylistItemsAsync：
并行取指纹(mtime+size, ≤4线程) → LoadTrackIndex 批量查索引(分块400) → 只对未命中做
TagLib 解析 → 全部条目进 `_playlist` → PersistTrackIndex 后台写回。
README 实测索引命中约 9.5x 提速（3609 首冷启 ~14s → 热启 ~1.5-2s）。
歌曲 ListView 虚拟化默认开；文件夹树懒加载(ChildrenLoaded)。

### 上万首瓶颈定位（按严重度）
1. **整库物化进内存**：_playlist 全量常驻，粗估 ~0.7-1KB/首 → 10万首≈100MB；
   且 LoadTrackIndex 加载期还有一份全量字典副本。排序=全量拷贝+整表替换（已优化过一趟）。
2. **CountLibraryStats 跑在 UI 线程**（MainWindow.GeekShell.cs:217）：全表 SELECT 所有行 +
   **逐条 File.Exists**，极客模式每秒定时器里每 15 次触发一次。1万首在机械盘/网络盘上
   直接卡界面。
3. **专辑封面逐张顺序提取**（MainWindow.Library2.cs RefreshAlbumViewAsync）：foreach+
   await Task.Run 一张一开文件，无磁盘缓存，切专辑页封面慢慢蹦。
4. **会话全量路径清单**：SaveSessionInternal 把全部路径 \n 拼接进**单个 TEXT 单元格**整体重写，
   1万首≈800KB/次。
5. 标签面板（TagPanelControl）是**独立全量列表**，不走 SQLite 索引，BuildEntry 每首必开 TagLib
   （与 Kid3 装文件夹一样的行为，可接受但要心里有数）。

### 标签编辑 vs Kid3 差距（TagEditorService.cs + TagPanelControl.xaml.cs）
- 现方案=「读全量9字段→改1个→全量写回→file.Save()」，每次单元格提交=开+读+写+存各一遍
  （CommitCellEditAsync:1672）。
- **多值字段被压扁**（真数据丢失）：SaveTag 里 `Performers=new[]{artist}`、
  `Genres=new[]{genre}`、`AlbumArtists=new[]{...}` 整体替换；读侧只用 FirstPerformer/
  FirstGenre/FirstAlbumArtist。多艺术家/多流派文件每次保存只剩第一个。
- Comment/Lyrics 同样只取第一个（多 USLT 帧丢其余）；ID3v2.4→2.3 每次保存强制降级重编码。
- 没有字段级脏标记：没碰的字段也随模型整体回写，TagLib 不认识的帧/APE 项有丢的风险。
- 已做得好的：阶段六快照整体回滚、阶段七批量工具、ReadTagRaw 取磁盘真值、封面管理齐全。

### 给出的方向（未动手，等用户拍板）
