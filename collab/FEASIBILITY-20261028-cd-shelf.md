# 自定义分类实体 CD 架：可行性方案

日期：2026-10-28。结论：**可行，适合作为 Celeste 专辑库的一种独立浏览视图。** 本轮只评估和设计，不新增书架页面、不改音乐文件或标签。

## 想做成什么

用户选定分类字段和次序，系统把专辑分到架子的格子里。每张专辑以有厚度的 CD 盒摆放：平时看盒脊，指向时轻微突出，选中后抽出、转正，显示封面和专辑信息；点击进入现有专辑详情或播放。

例如：

```text
架子方案：按流派分格 → 格内按专辑艺人 → 发行年份 → 专辑名
┌ Rock · 74 张 ────────────────────────────────────────┐
│ [盒脊][盒脊][盒脊][盒脊]   ← 指向后抽出一盒显示封面 │
├ Jazz · 31 张 ────────────────────────────────────────┤
│ [盒脊][盒脊][盒脊][盒脊][盒脊]                       │
├ 未分类 · 12 张 ──────────────────────────────────────┤
│ [盒脊][盒脊]                                         │
└─────────────────────────────────────────────────────┘
```

也可以先按艺术家首字母分格，再按艺人/年份排列；或者先按十年分格。分类字段、分类值的显示顺序、格内排序、架子材质和盒脊显示内容分别设置，避免混为一个“排序”开关。

## Rhine 能参考什么，不能直接搬什么

已检查本机 `Rhine-Music-Database-0.3.0` 的 README、预览图、`Qt/qml/Main.qml`、`Qt/src/RhiScene.h`、`DiscGeometry.h/.cpp`、`SceneTypes.h`、`Engine.cpp` 和 `Resources/slots.json`。

- 它的主画面是真正带透视、厚度、遮挡关系的成排盒子，选中盒子会突出；不是给普通卡片加一张阴影图片。
- `RhiScene` 使用 Qt 的 `QQuickRhiItemRenderer`，`DiscGeometry` 构造光盘环面并有中心孔、盒内光盘等几何参数；`slots.json` 与 Engine 负责内容槽位/分类入口。
- 值得借鉴的是构图、选择与抽取的连续动作、盒子的侧面/正面，以及分类和视觉位置的关联。
- 它的分类示例包含歌曲、歌单、收藏入口，不等于已经提供用户要求的“任意专辑字段自动分格”。Celeste 仍需自己的规则和保存格式。
- Celeste 当前是 WebView2 + 原生 JS/CSS，Rhine 是 Qt/QML/C++。不需要把 Qt 或其整套场景引擎带进播放器，也不直接复制其美术资产。

## 我们已有的数据够不够

| 能力 | 当前基础 | 还需补的部分 |
|---|---|---|
| 专辑列表 | `MainWindow.WebTransport.cs:WebAlbums` 已有专辑 id、名称、专辑艺人、年份、封面、歌曲数、曲目 id 与来源 id | 可复用现有专辑聚合，不另扫一遍磁盘 |
| 专辑封面 | 封面虚拟地址与分辨率档位已具备 | 盒脊用小图/取色，抽出后再请求大封面 |
| 专辑播放/详情 | 现有 `albums.js` 和共享播放接口 | 架子点击委托现有动作，不持有第二个引擎 |
| 字段分类 | 专辑艺人、年份、来源、名称可直接用 | 流派需从曲目汇总；评分要先定义是歌曲平均还是独立专辑评分；任意自定义字段需要增加索引/用户数据存储 |
| 保存方案 | 可以独立保存用户视图偏好 | 新增架子方案文件，和音乐标签、普通播放列表、外观预设分开 |

当前专辑 id 按来源、专辑名、专辑艺人计算。编辑这些标签后 id 可能改变，因此“手动摆放”不能只存旧 id 就永远不管；需要库更新时的重绑定/失效提示。不能把这个问题留到用户摆完几百张以后才发现。

## 分类规则必须先定清楚

1. **分格**决定专辑进入哪一格；**格内排序**决定那一格里 CD 的先后。两者独立，支持多级字段和升/降序。
2. 文本按自然顺序和拼音/字母规则排序，数字按数值排序；“2”应在“10”之前。艺术家首字母/年代等属于派生分组，不必改原标签。
3. 空值进入“未分类/未知年份”，不悄悄丢掉专辑。
4. 同一专辑有多个流派时，默认只在主流派放一个实体盒；其它流派可用筛选/引用入口。可选“多格展示同一专辑”，但要标明引用，不能算成多张收藏。
5. 曲目年份/艺人标签不一致时，需要可解释的专辑汇总规则。建议默认取专辑级代表值，异常时给整理提示；不要静默按某一首歌随意分格。
6. 新音乐加入或标签修改时，只更新受影响格子；保持当前选中、滚动与相机位置。

### 自动规则与手动摆放

建议第一版先做“按规则摆放”，同时允许调整分类格子的先后顺序。

第二步增加“个人手动摆放模式”：拖动只保存显示位置或置顶，不修改音频文件的流派、艺人、文件夹。把一张 Rock 专辑拖进 Jazz 格时，应明确这是个人陈列位置，不能偷偷改它的真实 Genre。真正改标签仍走专门的标签编辑流程。

同一个专辑库可以保存多个架子方案，例如“按流派”“按年代”“我最喜欢的专辑”。切换方案只改变浏览视图，不复制文件、不重建曲库、不打断播放。

## 技术路线比较

| 路线 | 能做到什么 | 成本/边界 |
|---|---|---|
| HTML/CSS 立体盒 + 虚拟化 | 固定视角、轻透视、盒脊/封面、悬停与抽出、格子和标签；容易接现有页面 | 适合首个可用版本。只对可见盒子建 DOM；大量独立 3D 图层或自由相机会带来性能压力 |
| WebGL 场景 + HTML 操作层 | 更接近 Rhine 的成排实体感、相机移动、遮挡、批量实例绘制、CD 盒开合 | 需要几何/材质/选中命中/纹理缓存与上下文丢失恢复；投入更高。若目标是大量盒子同时呈现或自由观察，优先评估这条路线 |
| 搬进 Qt 原生场景 | 可沿用另一套技术体系 | 对当前 WinUI/WebView2 工程引入双 UI 栈，集成和维护代价大，本项目不建议采用 |

**推荐**：先用少量真实专辑验证固定视角的盒子质感与交互，再决定正式渲染器。如果用户期待接近 Rhine 的深透视、大范围盒海和自由观察，正式版采用 WebGL；如果主要是“分类格子里一排 CD，抽出来看”，受控 CSS 3D 就可能足够。不要未经性能测量就承诺全部 3D 效果都能恒定 60fps。

这里不立即加入 Three.js 等新依赖。若 WebGL 试验确认需要渲染库，再单独选择实现和许可证；UI 仍保留现有原生 JS，不引入 React/Vue。

## 性能与交互底线

- 不一次解码所有高清封面。约 578 张专辑若全部解码成 480×480 RGBA，单是像素就约 **508 MiB**，还不含其它缓存。应只加载可见格子和少量相邻格子，抽出盒子才使用大图。
- 盒子共享几何与基础材质；远处盒子只画盒脊，近处/选中盒子再增加封面和细节。透明塑料与阴影采用可降级效果，不把昂贵的折射/物理模拟设为浏览必需。
- 分组/排序在数据层一次完成，场景只接收改变的专辑/格子；播放进度更新不得让全架重排。
- 只有拖动、抽出、转正或相机移动时持续动画；静止或页面隐藏时停止渲染循环。低性能模式关闭透视/反射，保留分类与选择能力。
- 支持搜索直达格子和专辑、方向键选盒、Enter 打开、Esc 放回；长盒脊可查看完整文字。不能只有鼠标悬停才能知道是哪张专辑。
- 保留普通专辑网格入口；书架是新增浏览方式，不取代可访问的列表/网格。

## 建议的开发阶段

1. **规则验证**：用真实库生成分类格与排序结果，验证空值、多流派、多碟、同名不同艺人/来源。
2. **视觉原型**：选 30–60 张真实专辑，做一个可抽出的格子，验证盒脊阅读、封面、滚动、宽窄窗口与减少动画。
3. **正式浏览器**：接完整库、分组编辑、搜索、保存方案、增量更新、可见区加载；根据原型性能决定 CSS 3D 或 WebGL。
4. **可选增强**：个人手动陈列、CD 盒开合、光盘抽取、自定义架子材质/光照。它们不阻塞基础书架使用。

拟新增 `shelf.js/shelf.css` 或隔离的场景渲染模块、`MainWindow.WebShelf.cs` 和版本化架子方案存储；复用 `WebAlbums`、封面资源与播放接口。方案至少保存分组字段、分组顺序、格内排序、格子容量、视觉样式、手动覆盖和版本号；不要存不可适配窗口尺寸的整屏绝对像素坐标。

**可行性结论**：数据和播放基础已具备；主要工作在规则设计、书架交互与场景性能。无需重写播放器或把音乐搬进一套新数据库，可以先以独立、可回退的专辑浏览视图落地。
